# Roll back to the previous release manifest

**Triggered by** `Any deploy-correlated incident; SLOErrorBudgetBurnFast; GatewayErrorRatioHigh`
**Severity** Any · **Owner** on-call

## The manifest is the rollback unit

A release is a **manifest** - `org/releases/<version>.yaml` in `micro-org`,
generated by `cfctl release`, naming exactly which image *digest* of each
service is in this release. Rollback is applying the previous manifest. It is
not `git revert` in one repository.

**A release name is `<year>.<month>.<sequence>`** - `2026.08.21` is the
twenty-first release cut in August 2026, not 21 August. **Do not sort those names
by hand to find "the previous one."** The sequence is not zero-padded, so
`2026.08.21` sorts before `2026.08.6`; and `org/releases/` still holds the
retired semver lineage (`2.3.0`..`2.5.19`) alongside the dated one, which no
comparison of two filenames can order at all. `2026.08.12` looked like the
successor of `2026.08.11` and was six days behind `2.5.19`; deploying it rolled
45 services back with everything healthy and every digest real (micro-org#384).
Ask the tool:

```sh
cd /home/savvaniss/dev/cloudsforge/deploy      # app host, inside WSL
./scripts/release-deploy.sh --list             # manifests, in the order they were cut
./scripts/release-deploy.sh --rollback         # the previous one, applied
```

**On the app host `savva@192.168.1.129`, not the chain host.** `192.168.1.42`
runs the chain daemons and has a `deploy` checkout of its own with no app stack
in it; a release command there does nothing an operator would notice until they
look for the change that did not land.

## Mitigation precedes diagnosis

If a release landed inside the incident window, roll back **before** diagnosing.
The deploy annotation on Platform overview is what tells you; it is posted by
`cfctl release` and it is the single most valuable mark on any of these
dashboards.

## Order

1. Confirm the correlation: does the metric turn at the annotation, or before it?
   Rolling back an unrelated release costs an hour and teaches the wrong lesson.
2. Roll back to the previous manifest.
3. Watch the SLI, not the deploy. A rollback that completes is not a rollback
   that worked.
4. If the schema changed, a rollback is NOT sufficient on its own - expand and
   contract discipline means the old code must still read the new schema. If it
   cannot, this is a forward fix rather than a rollback, and say so in the
   channel.

## Then

Freeze the service until the cause is understood. A second deploy on top of a
rolled-back one during an incident is how two problems become one confusing one.
